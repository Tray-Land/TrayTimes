# Tray Times

Click the tray icon for live Milwaukee County Transit System (MCTS) bus arrivals. Click away and the flyout closes. Hovering over the icon shows the next arrivals at your first three favorite stops.

- **Launching:** the first manual launch opens Settings if no stops or places have been saved. Later manual launches open the arrivals flyout, even if you haven't saved anything yet. Launching it again opens the running instance's window instead of starting another instance. With **Start with Windows** enabled, Windows sign-in launches stay in the tray without opening a window and don't consume the first-launch setup.
- **Favorites:** your favorite stops, with arrivals, route lines, and the approaching buses on the map. Pick stops in Settings (Route → Direction → Stop, or tap a stop on the map), or star one from the other tabs.
- **Settings:** a Mica-backed window groups **Your commute**, **Bus alerts**, and **App & data** into native cards and expanders. Favorite stops stay open when you have saved stops; otherwise **Add a stop** opens for setup. Places, the stop directory, API usage, and credits expand when needed. Alert and startup preferences apply immediately.
- **Bus selection:** click an arrival with a live bus location to frame the stop and bus on the map. The selected bus has a larger yellow background, which stays highlighted as its position updates. A solid arrowhead beside each bus shows its live heading, when available, and stays aligned with the map as it rotates. Tapping a bus marker also selects it; selecting another bus moves the highlight, and selecting a stop or showing all listed stops clears it.
- **Commute:** the buses for your likely next trip. Away from home, it shows the buses that take you home; at home, the buses to work (or school, or your first custom place). It lists only routes that get there in one ride, heading the right way, within about a 10-minute walk at each end. If Windows location is off, it guesses from the time of day (mornings start at home). "Going to" picks a different place for now. Set your favorite places (Home, Work, School, and any custom ones) in Settings.
- **Nearby:** the same view around your current location, from Windows location services. It dims buses that will leave before you can walk to the stop.
- **Location permission:** Commute and Nearby check access without opening a prompt. When permission is needed, use the **Grant Location Permission** banner to open the Windows permission prompt or location settings. The flyout stays open while you grant access and retries location and arrivals when you return; normal click-away dismissal resumes afterward. Favorites doesn't need location permission.
- **Arrivals and bus locations:** the MCTS BusTime Developer API v3 (`realtime.ridemcts.com`). The API guide is `../DeveloperAPIGuide3_0.pdf`.
- **Stop directory:** BusTime can't search stops by location. The app crawls every route's stops about once a week (around 100 requests) and caches them in LocalState. Settings has an "Update now" button.
- **Scheduled times:** MCTS's GTFS timetable (`kamino.mcts.org/gtfs/google_transit.zip`, about 9 MB). It's downloaded to LocalState, checked for updates weekly, and read into memory while the flyout is open. Where BusTime has no prediction (it only looks about 30 to 60 minutes ahead), rows show the scheduled time instead, labeled "Scheduled" and without the tracking bell. The GTFS route and direction IDs are matched to BusTime's using the stop directory.
- **Basemap and address search:** Azure Maps, with the map rendered by [WinUIEx.Maps](https://github.com/dotMorten/WinUIEx.Maps).

The transit code sits behind `ITransitService` (`TrayTimes.Core/Transit/`), so another provider such as Transit.app can be added later without changing the UI.

## Project layout

- `TrayTimes/`: the WinUI 3 app. `Views/` and `Controls/` hold the UI; `Services/` holds code that needs Windows (settings storage, location, the stop directory cache, tray placement).
- `TrayTimes.Core/`: plain .NET code with no WinUI or Windows dependencies. `Transit/` has the provider-neutral models, the BusTime client, and the GTFS timetable reader; `Models/` has the favorite stops and places and the arrival snapshots; `Commute/` works out the likely next trip and its direct routes.
- `TrayTimes.Tests/`: MSTest unit tests for `TrayTimes.Core`, laid out to mirror it. Run them with `dotnet test TrayTimes.Tests`. They need no API key or package identity.
- **Request diagnostics:** the BusTime client's `Diagnostics.Observed` event and bounded `Diagnostics.Snapshot` (last 256 observations) distinguish physical request starts/completions from existing cache/task reuse, with consumer, trigger, duration, outcome, and batch size. Debug builds also emit credential-safe `Transit request` lines to the debugger. The saved Settings endpoint tally still counts attempts, including failures, not cache hits or server billing. Reproducible baseline procedures and measurements are recorded in [the optimization plan](docs/transit-api-optimization-plan.md).

## Setup

1. In `TrayTimes/`, copy `OAuth.resw.sample` to `OAuth.resw`. That file is gitignored.
2. Put your MCTS BusTime key in `MctsApiKey`. Optionally, put an Azure Maps key in `AzureMapsKey` for the basemap and address search.
3. Run from `TrayTimes/` with `dotnet run -c Debug -p:Platform=x64` (or `ARM64`). Tray apps keep running after `dotnet run` returns only when launched detached: `winapp run . --detach --arch x64`.

### Command-line builds

From the repository root, `winapp run .\TrayTimes\TrayTimes.csproj --detach` builds and launches for the current machine's architecture. `build-msix-for-gh.ps1` publishes x64 and ARM64 MSIX packages, signs them using the maintainer's local `sign-msix` function, and creates a draft release; pass `-SkipRelease` to build and sign without tagging or uploading.

Keep named controls distinct from properties used by `x:Bind` in data templates. For example, the flyout's `EmptyStateText` control must not be named `EmptyText`, which is a bound `StopGroupItem` property. That collision produces WMC1507 in Visual Studio; the standalone XAML compiler used by CLI builds instead fails with WMC9999 while loading the warning's error-message resource.

## API budget

**Shared metadata.** Routes, directions, and provider-ordered stop lists are reused for seven days; route shapes for six hours. These bounded caches and in-flight loads belong to the app, so closing/recreating Settings or the flyout does not discard valid metadata. A complete new directory build also persists picker metadata in LocalState. Older or partial directories still serve geographic lookups but fall back to shared endpoint loads for the picker, because they cannot prove route names, completeness, or stop ordering. "Update now" invalidates metadata before rebuilding; failures remain retryable. The Settings stop picker and map dots become usable as soon as stops arrive, independently of route shapes; shape failures report status without disabling stop selection.

The default key allows 10,000 requests a day. While the flyout is open, arrivals refresh every 30 s and bus positions every 15 s. Favorites, Commute/Nearby, and tracking share pending predictions and suitably fresh stop-scoped results, including successful empty responses. Known browsing stops due together share batches of up to ten; larger unions fetch every stop in multiple batches. Favorites still updates the tray tooltip while another tab is selected. Tracking uses its own freshness interval and never expands its faster requests to unrelated browsing stops. The app retains at most 128 live stop snapshots; reuse keeps the original fetch timestamp.

Equivalent overlapping vehicle refreshes share one request; ordinary events reuse successful positions younger than 15 s. A changed displayed bus set refreshes immediately, and manual refresh/F5 bypasses prediction/position freshness but still shares in-flight work. Browsing timers stop as soon as the flyout is dismissed; abandoned prediction waiters cancel only HTTP work no other consumer needs. After a minute the flyout closes and releases its cached positions. Tracking (the bell next to an arrival) keeps only that stop refreshing while hidden: every 60 s, then every 30 s under 10 minutes out and every 10 s under 5, until 5 minutes after the bus is first due.

**Passed-bus recovery.** Two distinct consecutive successful prediction snapshots without the due bus confirm passage and show the slash badge; only then do tracking checks slow to every 30 s. Reusing the same cached response cannot confirm twice, and a failed/canceled fetch resets unconfirmed evidence without claiming passage. A matching bus returning clears the slash and restores normal polling; a matching cancellation still sends its alert and stops tracking. The original five-minute grace, due display and keep-awake lifecycle do not restart. Confirmed-passage checks use 30 rather than 10 s; shared snapshot age and response latency can delay recovery/cancellation observations further, and brief events between checks can be missed. In the deterministic immediately absent trip, grace-period requests fall from 30 to 11 (12 timer checks, with the last reusing fresh data); later disappearance, recovery, failures and shared browsing traffic change the actual saving.

**Failures and cancellation.** One failure cooldown wraps every BusTime call. After a network, timeout, or server failure, timer-driven refreshes make no request for 15 s, doubling to a 5-minute cap on repeated failures; a success resets it, and requests that fail together count once. Held requests report the usual "can't reach" state and are recorded as suppressed in the diagnostics, never as empty results. Manual actions (refresh, F5, reopening the flyout, changing tab/destination/stops, picker selections) skip that hold but are spaced at least 5 s apart after a failure, so rapid hide/show cannot storm the service. Tracking is never delayed by an ordinary cooldown. A 429 (or a 503 with `Retry-After`) or a daily-quota error pauses every request for the server's `Retry-After` (60 s if absent; quota 5 minutes; never more than an hour). A rejected key or HTTP 401/403 pauses timers and tracking for 30 minutes, allowing one manual retry after the 5 s spacing. Query-level API errors (such as one unknown stop) never start a cooldown. The stop-directory crawl runs once at a time, stops early on a rate limit, rejected key, cooldown, or when over a quarter of routes fail, and an automatic rebuild after a failed one waits 5 minutes (doubling to an hour); "Update now" bypasses that wait but joins a build already running. Closing the flyout or Settings cancels their in-flight route drawing, picker, walking-route, and place-discovery requests; the shared directory crawl is deliberately not cancelled. Error classification of BusTime body messages ("access key", "api key", "exceeded", "rate limit") is a heuristic, because BusTime's documentation does not specify these responses.

Commute/Nearby retains validated stop discovery during the flyout's one-minute warm lifetime. Quick reopen shows valid last-known rows immediately; routine predictions refresh without waiting for a new location or walking route. Independent location checks repeat discovery only for meaningful movement (over 25 m), changed destinations/places, a changed stop directory, or missing discovery. A precise fix with the same stops updates walking metadata without repeating fresh predictions. Commute confirms direct directions only with a route shape; required shape failures retain last-good data with the existing error status rather than guessing a direct ride.

When GTFS finishes loading (including a reload of the cached feed), Favorites and Commute/Nearby re-merge applicable raw live predictions locally. Scheduled rows and commute destination estimates appear without another prediction request. This preserves the live fetch timestamp, freshness age, and any current error; normal timed/manual refreshes are unchanged. With no applicable snapshot, the normal coordinated refresh supplies one.
